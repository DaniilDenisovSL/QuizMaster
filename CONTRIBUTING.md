# Правила командної роботи Quiz Master

Статус: пропозиція Team Lead для погодження командою.

## Гілки

- `main` — стабільна версія для демонстрації.
- `develop` — інтеграція поточної роботи.
- `feature/<назва>` — нова функція, наприклад `feature/quiz-menu`.
- `fix/<назва>` — виправлення помилки.
- `docs/<назва>` — документація.

Робочі гілки створюємо від актуальної develop. Одне завдання — одна гілка й один Pull Request у develop. Після інтеграційної перевірки Team Lead відкриває Pull Request із develop у main. Після початкового налаштування напряму в main і develop не пушимо. Force push у спільні гілки заборонено.

## Порядок роботи

1. Вибрати свою картку Trello та перевести її в «У процесі».
2. Оновити develop і створити робочу гілку:

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/quiz-menu
```

3. Виконати завдання, зібрати проєкт і перевірити змінені функції.
4. Додати лише файли завдання; перевірити `git diff --staged`.
5. Створити коміт і відправити гілку:

```bash
git commit -m "feat: add quiz menu"
git push -u origin feature/quiz-menu
```

6. Відкрити Pull Request у develop: опис змін, спосіб перевірки, посилання на Trello; для інтерфейсу додати знімок екрана.
7. Перевести картку в «На перевірці». Team Lead перевіряє код, Tester перевіряє поведінку. Код Team Lead перевіряє інший розробник.
8. Виправити зауваження в тій самій гілці. Після перевірки та злиття картка переходить у «Готово».

## Коміти

Формат: `тип: короткий опис`. Один коміт — одна зрозуміла мета.

| Тип | Призначення | Приклад |
| --- | --- | --- |
| feat | Нова функція | feat: add answer validation |
| fix | Виправлення | fix: stop timer after game over |
| docs | Документація | docs: describe game rules |
| test | Тести й сценарії | test: add score calculation cases |
| refactor | Структура без зміни поведінки | refactor: extract quiz service |
| chore | Налаштування | chore: add gitignore |

Не використовуємо назви update, 123, final. Не додаємо паролі, токени, персональні налаштування, bin та obj.

## Windows Forms

- Домовляємося перед одночасним редагуванням однієї форми.
- Зміни форми зберігаємо разом: FormName.cs, FormName.Designer.cs та FormName.resx, якщо вони змінені.
- Designer.cs та resx потрібні в репозиторії.
- Після конфлікту перевіряємо збірку і відкриття форми в дизайнері.

## Критерії готовності

Вимоги картки виконано; проєкт збирається; змінені функції перевірено; результат записано у PR або Trello; зауваження усунено; зміни злиті; документацію оновлено за потреби.
